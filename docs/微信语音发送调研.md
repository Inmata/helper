# 微信语音发送调研

核对日期：2026-11-10。以下以本 fork 的 `a0aed45` 为调研基线。目标是在 Windows 微信 4.2.0.12 的会话中发出可点击播放的原生语音条（消息类型 `34`），保留群语音接收和转写。

**推荐参考 `Prometheus-first/helper` 的 Windows 原生发送实现。** 上游 `main`（`be370c1`）与本 fork（`a0aed45`）登记的 4.2.0.12 核心 DLL 文件大小和 SHA-256 一致。上游已经实现 `voice.send`，并在该版本的文件传输助手验证过发送。群聊和好友共用目标接口，源码及离线测试覆盖目标传递；公开文档没有单独记录 Windows 4.2.0.12 群聊发送后由接收端播放的验收。[本地构建配置](../native/compatibility.json) · [上游构建配置][build] · [上游语音说明][voice] · [发送服务测试][test]

| 实现 | 实际行为与适用范围 |
| --- | --- |
| `Prometheus-first/helper` Windows `main` | 将支持的单声道 16-bit PCM WAV 转为腾讯 SILK，或直接准备已有 SILK；原生桥接发送类型 `34`，不依赖前台录音。输入上限 20 MiB、单条上限 60 秒；入口返回微信是否接受发送。4.2.0.12 的好友私聊实测项目是接收与撤回补发。[语音说明][voice] · [原生桥接说明][native] |
| `Prometheus-first/helper` Linux 分支 | Linux 微信 4.1.13.26 有群聊实测：1 秒测试音由接收端确认可播放，另有群短语音撤回后单次补发且可播放的记录。该证据限于 Linux 构建。[Linux 实测结果][linux] |
| `ChisBread/wechat-ai` | Docker 中的 Linux 微信 4.1.13，经 PulseAudio 虚拟麦克风播放音频，再由微信界面录制和发送，产物是原生语音条。实现依赖可见界面、浅色主题和 100% 缩放；项目以外发语音记录核对结果，接收端播放需另验。[发送说明][rpa-doc] · [录音动作源码][rpa-code] |
| `Tencent/openclaw-weixin` | 走另行绑定的 iLink 机器人会话。当前出站代码将音频发成普通文件附件；公开实测中，直接提交协议的 `VOICE` 项曾获得成功返回，微信客户端却没有显示语音条。[会话绑定说明][ilink-doc] · [媒体发送源码][ilink-send] · [实测记录][ilink-issue] |

当前 fork 只接收并转写群语音：`WxPollMediaMessageWithVoice` 读取随消息到达的 SILK；缺失时按原消息编号补取，再由本地识别器写入聊天上下文。`NativeTextService` 和发送层已有文本、图片发送入口，尚未接入语音发送。上游使用更新的 `WxPollMediaMessageV7` 接收布局，两侧服务与桥接已分叉；直接替换 DLL 或照搬整套服务会把接收链一并换掉。[本地消息规范](../.spec/messages/spec.md) · [本地原生服务](../native/text_service.py) · [本地发送层](../wxbot_framework/messaging/delivery.py) · [上游原生桥接说明][native]

后续若接入，优先参考上游的音频准备模块 `voices.py` 和 `voice_send.h` 的类型 `34` 发送能力，沿本 fork 的原生桥接、后端适配和发送层接线。保留群语音补取、转写以及现有的连接与账号校验；本 fork 的 `requirements-voice.txt` 已列出与上游相同的 `silk-python==0.2.8`。先用文件传输助手复现，再在授权测试群确认接收端显示原生语音条且可播放，并检查原有群语音转写。Fish Audio 合成回复是上游可选插件，可以独立于发送能力考虑。复用上游代码适用该版本的非商业许可。[音频准备][prepare] · [上游发送服务][service] · [上游发送层][sdk] · [本地语音依赖](../requirements-voice.txt) · [上游许可][license]

## 本仓库接入验收

2026-11-10，Windows 微信 4.2.0.12 使用本地控制台发送同一份 1.2 秒 WAV。文件传输助手和原群均收到类型 34 的提交成功回执，群内手机端确认显示为语音条、两声短音均可播放。
