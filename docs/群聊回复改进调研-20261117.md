# 群聊回复改进调研

日期：2026-11-17。范围：一手资料调研及当前架构下的设计建议。本文记录设计阶段的一手资料；后续实施与验证见[实测记录](群聊回复改进实测-20261117.md)。

## 结论

建议保留现有 Python、SQLite、Jev、慢回复队列和原生微信桥接，在六个边界补齐行为：

1. **把回复必要性、查证必要性、候选答案依据分开。** 当前问题需要查证时，候选答案写成“不知道”仍应进入搜索判断；有无无依据断言用于决定是否修订。
2. **成员偏好写入结构化设置，由发送代码执行。** 自然语言只负责识别“以后只发文字”等操作；提交成功后再确认，后续每种回复路径读取同一设置。
3. **确认状态按连接、群、发言者归属。** 插话可继续走普通消息链路；只有确认、明确取消、替换、过期等事件消耗待确认状态。
4. **后台生图任务及其产物进入可回查状态。** 聊天能读到真实阶段；引用看图和引用编辑共用同一媒体定位结果。
5. **用一轮共享截止时间和有限调用次数控制延迟。** 到期有明确结束原因；迟到结果在发送前检查任务状态，不再开启新校验或新搜索。
6. **图片发送成功、可引用、可再次编辑分别验收。** 当前 `send_image` 的布尔结果没有提供服务器消息编号；必须补实发送图片与引用 `svrid` 的关联证据。

人物相关上下文检索应覆盖所有聊到具体成员的场景：由 Jev 结合指代、当前话题和已有资料判断需要哪些上下文，程序按已确认身份取相关原话。人物评价是其中一个实例，入口不依赖“评价”等关键词。

这些是本项目的建议。下文把外部项目已实现的模式、可借鉴部分和仍待验证的本地条件分别列出。

## 1. 查证必要性与答案依据分开

### 一手实现

Haystack 的 `ConditionalRouter` 根据输入条件选择后续输出；`FaithfulnessEvaluator` 独立接收问题、资料和候选答案，把答案中的陈述逐项与资料对应。源码示例专门包含“答案一部分有资料支持，另一部分额外加入人数”的情况。Agent 的步数控制又独立于上述两类组件，达到上限时写入 `exit_reason=max_agent_steps`。来源：[路由输入与输出](https://github.com/deepset-ai/haystack/blob/f21f3c0269950836a21cf67b6976c7e406ac6b11/haystack/components/routers/conditional_router.py#L41-L85)、[依据评价的输入和示例](https://github.com/deepset-ai/haystack/blob/f21f3c0269950836a21cf67b6976c7e406ac6b11/haystack/components/evaluators/faithfulness.py#L17-L60)、[有限步数与退出原因](https://github.com/deepset-ai/haystack/blob/f21f3c0269950836a21cf67b6976c7e406ac6b11/haystack/components/agents/agent.py#L949-L970)。

### 建议落点

沿用 Jev 的一次结构化请求，可以同时返回几个独立判断；控制流分别使用，避免通过相互叠加的条件把某个判断屏蔽：

| 判断 | 主要输入 | 决定的动作 |
|---|---|---|
| 本轮是否应答、需要什么答案 | 当前问题、引用、会话上下文 | 普通回答、澄清、闲聊、无需回复 |
| 回答是否依赖外部查证 | 问题、必要条件、时效性、已有资料是否覆盖 | 搜索，或询问缺失的游戏/版本等关键条件 |
| 候选答案是否增加无依据断言 | 候选答案、群友原话、已取得资料及其来源 | 删除多余断言或有限修订 |
| 候选答案是否完成用户请求 | 当前问题与候选答案 | 防止用接梗、附和或泛泛安慰替代答题 |

其中最后一项是本项目建议，本次来源没有直接实现此群聊验收规则。

建议先判断问题所需依据，再组织答案。若候选正文只说“不清楚”，查证分支仍按问题本身决定。若正文增加了无关机制、病因或个人动机，删除该断言；不为模型自行添加的枝节扩大搜索范围。用户问法中的前提、历史机器人发言、玩笑和当前可核对事实分别标明来源。

**取舍：** 依据评价验证的是“资料是否支持这句话”，资料的可靠性、日期和适用版本还需要搜索阶段判断。每句话都增加一次模型调用会扩大延迟；本项目宜沿用现有合并判断，一轮共用调用上限，并把重复改写、事实校验和补查计算在同一个预算中。

TypeSafe 的官方 `citation_check` 示例与现有 Jev 更贴近：先用程序确认逐字引用存在，再把实际原文上下文和主张交给 `Choice`，区分支持、矛盾、未涉及。示例的概率用于决定是否接受这次判断或继续复核。本项目可沿用“先取真实原文，再判断支持关系”的顺序；口语概括须按语义核对，不能套用逐字引用的存在检查。群聊中无需强制输出网址或逐句附引用。来源：[TypeSafe 引用核对](https://docs.typesafe.ai/cookbooks/citation_check)。

## 2. 持久偏好成为程序状态

### 一手实现

Rasa 的 `SlotSet` 是带键和值的事件，应用时更新 tracker 中的槽位；`SQLTrackerStore.save` 把事件按 `sender_id` 写入数据库，查询按事件 ID 顺序恢复。该模式明确区分自然语言理解结果、已提交状态和后续动作。来源：[SlotSet](https://github.com/RasaHQ/rasa/blob/60a3cff9c08183760355b07bd60f5223d8916d6b/rasa/shared/core/events.py#L960-L1045)、[SQL 存取](https://github.com/RasaHQ/rasa/blob/60a3cff9c08183760355b07bd60f5223d8916d6b/rasa/core/tracker_store.py#L1290-L1362)。

### 建议落点

当前项目已有按机器人账号、群、真实成员 ID 保存的语音设置，应在现有设置入口承接自然语言要求，避免另外建立“偏好记忆”系统。来源：[现有艾特回复规范](../.spec/mention-reply/spec.md)中“固定语音”约定。

- “以后只发文字”识别为持续设置；“这条用文字”仅影响本轮；“你说话太多”缺少发送形式的明确操作，不直接改设置。
- 默认只能改当前发言者自己的偏好；管理员修改他人设置沿用现有权限入口。
- 持续设置先写入，再给出确认。确认措辞必须对应实际提交结果。
- 选择文字/语音时读取已提交状态，覆盖普通艾特、连续追问、看图、搜索、澄清及冷处理实际回复等分支。
- 自然语言和现有命令调用同一设置方法；重启、改名和人格切换后仍按既有账号、群、成员作用域执行。

以上是适配建议，Rasa 的 SQL 事件存储仅提供状态化思路；本项目继续使用唯一 `Database` 和既有 `RoomStateStore`。

## 3. 确认可被插话打断后继续

### 一手实现

NoneBot 的 `User` 权限检查当前事件的 `session_id`，默认 `update_permission` 根据触发事件生成这项权限。`pause` 和 `reject` 后创建临时 matcher，携带剩余处理函数、原状态和过期时间；`reject` 把当前处理函数放回待处理列表。来源：[会话权限](https://github.com/nonebot/nonebot2/blob/2450b67a115916410d67154a8767b8e4c5aeb62f/nonebot/internal/permission.py#L114-L162)、[默认确认归属](https://github.com/nonebot/nonebot2/blob/2450b67a115916410d67154a8767b8e4c5aeb62f/nonebot/internal/matcher/matcher.py#L787-L809)、[状态和期限保留](https://github.com/nonebot/nonebot2/blob/2450b67a115916410d67154a8767b8e4c5aeb62f/nonebot/internal/matcher/matcher.py#L904-L945)。

Rasa 的 `LoopInterrupted` 用于标记填表过程中插入 FAQ 等分支。表单校验读取中断标记，返回表单时仍能确定下一项待填槽位；终止则使用明确的 `requested_slot=None` 或 `ActiveLoop(None)` 事件。来源：[LoopInterrupted](https://github.com/RasaHQ/rasa/blob/60a3cff9c08183760355b07bd60f5223d8916d6b/rasa/shared/core/events.py#L1820-L1846)、[FormAction 的恢复与结束逻辑](https://github.com/RasaHQ/rasa/blob/60a3cff9c08183760355b07bd60f5223d8916d6b/rasa/core/actions/forms.py)。

### 建议落点

复用 `MemberStore.profile_queries`，让“消息路由”和“确认状态是否作废”各自有明确规则：

| 新事件 | 建议行为 |
|---|---|
| 其他成员普通插话 | 原确认保留，该消息正常分发 |
| 原提问者明确选中候选 | 消耗确认，查询选中的档案 |
| 原提问者明确说取消 | 结束确认 |
| 原提问者发起新的同类档案查询 | 用新查询替换原确认 |
| 无关话题 | 交给普通消息路径，原确认在有效期内保留；避免见到任意话题变化就删除 |
| 过期、连接切换、清空等明确失效事件 | 按现有生命周期规则结束 |

不要求增加通用状态机框架。待确认内容仍保持只读选人，不改变陌生称呼与成员的身份绑定。具体过期时间沿用或另行确认，本文不设新数值。

## 4. 后台生图状态和自产图片回填

### 一手实现

Open WebUI 的 `create_task` 为协程登记 `task_id`，可关联所属 item，完成回调负责清理；`stop_task` 按任务取消。状态事件带 `chat_id` 和 `message_id`，并写入该消息的状态记录。来源：[任务登记](https://github.com/open-webui/open-webui/blob/b0e6098e940942281d9c83f3529ea117287a3a22/backend/open_webui/tasks.py#L143-L181)、[任务取消](https://github.com/open-webui/open-webui/blob/b0e6098e940942281d9c83f3529ea117287a3a22/backend/open_webui/tasks.py#L311-L367)、[状态归属和保存](https://github.com/open-webui/open-webui/blob/b0e6098e940942281d9c83f3529ea117287a3a22/backend/open_webui/socket/main.py#L1621-L1726)。

其 `generate_image` 和 `edit_image` 都在成功后构造图片附件，按 `chat_id+message_id` 写入消息，再发附件事件，并把图片信息返回工具调用方。生成与编辑使用一致的产物回填方式。来源：[生成图片](https://github.com/open-webui/open-webui/blob/b0e6098e940942281d9c83f3529ea117287a3a22/backend/open_webui/tools/builtin.py#L366-L445)、[编辑图片](https://github.com/open-webui/open-webui/blob/b0e6098e940942281d9c83f3529ea117287a3a22/backend/open_webui/tools/builtin.py#L448-L536)。

### 建议落点

现有生图 worker 持有任务事实，并提供轻量只读查询；聊天上下文读取实际阶段，避免靠旧回复猜测任务进度。阶段至少要区分排队、生成中、产物已就绪、发送中、已提交发送、失败和取消；只有收到相应证据才写入该阶段。

产物记录至少关联当前连接/账号、群、请求者、原请求、任务 ID、本地图片路径和实际可用的消息关联字段。媒体路径等内部字段只给程序与工具使用，群聊回复只描述状态。

两个用户场景共用媒体解析入口：

| 用户动作 | 解析后的用途 | 验收重点 |
|---|---|---|
| 引用机器人生成图，问“图里有什么” | 原图片交给看图工具 | 实际读到被引用的产物；不退回“没收到这张图” |
| 引用同一张图，要求改颜色、加物体等 | 原图片交给编辑/带参考图生成工具 | 工具调用确实含原图；新产物再次回填，可继续被引用 |

引用的优先级高于“最近一张图”。近期图片索引可以继续服务省略引用的口语请求，明确引用必须定位对应产物。是否跨重启保留自产图片引用能力，应作为单独验收项确定；若纳入，则映射需要与本地媒体一同持久保存，单靠当前进程内索引不够。

### 当前桥接必须补实的关联

本地源码 `NativeTextService.send_image` 最终返回 `self.last_result["success"]`；`RecentImages.quoted` 先按 `svrid` 匹配原消息编号，再按 `md5` 匹配当前群记录。当前发送结果没有向上层提供 `svrid`。来源：[native/text_service.py](../native/text_service.py)、[recent_images.py](../wxbot_framework/recent_images.py)。

公开 WeChatFerry 的图片发送同样返回状态码，没有在这个 API 返回图片消息 ID。它可帮助界定现有返回值的含义，无法补全当前桥接的缺口。来源：[WeChatFerry send_image](https://github.com/lich0821/WeChatFerry/blob/0f5c60a034fcac234cabd000b49c9200defa7f7d/clients/python/wcferry/client.py#L384-L403)。

下一轮实现前，先做定向关联验证：

- 核对当前微信构建发送图片时可取得的客户端编号、本地消息编号，以及本机发送消息是否产生可关联的接收回显。字段名称与获取位置以实际桥接为准。
- 对同一图片记录发送回执、回显和后续引用中的 `svrid`、`image_md5`，确认哪条链路能稳定关联。
- 微信可能处理发送文件；本地文件的 MD5 与引用 XML 中的图片 MD5 是否一致需要实测。仅在这种匹配实际用于图片选择时计算或保存它，不增加无用途校验和。
- 若回执存在客户端编号，可借鉴本项目已有语音回执和引用绑定的设计；图片的具体编号来源仍需核实。

已有本地图片路径即可记录产物，但服务器编号关联仍缺证据时，状态应明确标记“产物存在、引用映射待补齐”。此时验收还需完成真实引用看图及编辑；“生成并发出图片”与这两项分别记录。

## 5. 软进度、总预算耗尽、重试与迟到结果

### 成熟先例及边界

Open WebUI 的官方事件文档区分中间 `status` 与结束状态，并要求状态序列最终出现 `done: True`；该字段控制界面显示，后台任务生命周期需另行维护。来源：[官方事件文档固定版本](https://github.com/open-webui/docs/blob/87f884ee5c576edaeca38e3de5fe450ee28cb4ed/docs/features/extensibility/plugin/development/events.mdx#L156-L191)。

Python 3.12 提供绝对时间截止的 `asyncio.timeout_at`；`wait_for` 会等待取消真正完成，实际等待可能超过设定值。`concurrent.futures.Future.cancel()` 对正在执行的调用返回 `False`。这要求当前线程式工具调用分别管理等待截止、底层取消和结果有效性。来源：[asyncio 超时](https://docs.python.org/3.12/library/asyncio-task.html#timeouts)、[Future.cancel](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Future.cancel)。

Matrix 官方协议提供一个可对照的重试前提：客户端生成 transaction ID，服务端将同一端点的同一 ID 识别为重传，并返回原结果；本地发送回显也可通过 transaction ID 与服务器事件关联。当前微信桥接没有证实提供同类服务端去重能力，因此只借鉴“逻辑操作 ID 与发送结果绑定”的思路。来源：[事务编号](https://spec.matrix.org/v1.16/client-server-api/#transaction-identifiers)、[本地与远端回显](https://spec.matrix.org/v1.16/client-server-api/#local-echo)。

### 建议状态约定

“30 秒提醒、60 秒总上限”仍是待讨论数值。应先确定到期后的行为，再根据普通问答、搜索和生图的实际耗时分布定数值；一套时间不必覆盖所有任务类型。

| 阶段或结果 | 建议行为 | 迟到结果与重试 |
|---|---|---|
| 达到软提醒时刻，工作仍有效 | 至多发送一次真实进度，如正在搜索或生成图片；同一任务继续运行 | 提醒不新建任务、不重置总预算 |
| 普通回答/搜索预算耗尽，有足够的已核对内容 | 发出可支持的部分，并明确剩余缺口；结束本轮 | 原轮次后续模型结果不再发群；不继续补查或重复校验 |
| 预算耗尽，没有可用答案 | 给出简短失败原因和可执行的继续方式，结束本轮 | “重试”沿用明确目标启动新一轮；已成功取得的资料按有效期复用 |
| 生图等待时间较长，任务仍有效 | 可保持后台运行并报告真实状态；完成时经原守卫发图 | 该任务仍是活动状态，重复催促查询状态，不重复生图 |
| 生图达到自身任务截止或被取消 | 写入超时/取消终态，阻止该任务继续提交群发送 | 迟到产物只更新内部可回收结果；用户重新要求时再决定复用或新建 |
| 微信发送返回不确定，可能已提交 | 标记发送结果待核实，停止自动重复发送 | 先查关联回执/回显；未确认服务端幂等时不套用自动重发 |

“预算耗尽后给出结果”和“生图继续后台执行”是两种明确状态：普通回复结束后停止扩大工作；可继续的长任务在后台仍保留活动记录。若生图也已进入超时或取消终态，则按终态处理迟到结果。

### 最小实现原则

- 一轮入口创建共享截止时间，初次判断、搜索、回答、重复检测、依据修订和补查消费同一份时间；给最终状态通知保留独立、短且有界的路径。
- 用实际请求/轮次 ID 关联队列任务和状态。发送前复用现有 `delivery_guard`，同时检查轮次是否已结束、取消或被替换。
- 已在运行且无法取消的调用可完成清理，但结果提交必须再次检查任务终态；拒绝旧结果的发送，不额外起一个“最后校验”模型请求。
- 同一入站消息或同一活动请求重复投递时复用现有任务；“重试”是新的尝试，记录它所接续的原请求，避免把新尝试的进度覆盖成旧任务结果。
- 已有图片且仅发送明确失败时优先重用产物；发送结果不确定时先核实。生图提供方若没有任务查询和幂等键，重试的重复生成成本需要在行为设计中说明。
- 超时通知若仍完全依赖同一个已超时的聊天模型，就无法稳定闭环。建议允许程序输出简短事实状态；人格化正文继续由模型处理。

这些规则用于已出现的长等待、重复请求和异步结果场景。本文没有建议通用重试框架、分布式队列或额外防护层。

## 6. 聊到具体成员时检索其相关消息

### 已确认的素材缺口

`prefetch_mention_context` 预取提问者的身份、档案和记忆，再检索相关记忆与匹配人物；其中没有按本轮谈及成员的账号定向读取相关发言的步骤。当前全群上下文入口 `conversation_snapshot` 的默认 `group_limit=25`，与手册描述的“最近 50 条”存在漂移；本轮设计以实际 25 条为准。连续对话另取至多 40 条收发记录，其中包含机器人回复，并以 30 分钟无新消息作为连续性分界。这些上下文各有用途；涉及某人的经历、说法、偏好、近况或行为时，还需要取得与当前话题有关的本人原话。来源：[context_tools.py](../wxbot_framework/conversation/context_tools.py)、[members.py](../wxbot_framework/conversation/members.py)、[history.py](../wxbot_framework/conversation/history.py)。

本轮已有两条样本在提供六条目标原话后仍输出空泛回答；相关素材包含目标成员多次提出生图要求的记录。因此检索和生成质量需要分别验收。素材定位、论点形成、例证使用、风格压缩和审核输入都需要定向核对。短句长度及强调机器人自身情绪的提示词是待验证的影响因素；目前不把完整归因锁定到单一环节。

### 建议的最小补齐

- **所有人物相关场景进入同一上下文流程。** 姓名、昵称、引用中的人物及“他”“刚才那个人”等指代，结合当前话题解析。覆盖询问某人的观点、回顾某人的说法、聊其偏好或近况、比较、接续讨论和评价，不设置仅命中“评价”才检索的入口。
- **Jev 判断上下文需求和相关性。** 结合当前提问、引用、对话承接及已确认候选身份，判断本轮谈到谁、需要哪类信息、已有资料缺什么，并对取得的原话判断相关性。结果用于选择目标、话题和必要时间范围；具体取数和身份作用域由程序执行。
- **内部解析保留真实目标。** 当前 `lookup_people` 的公开结果主要是姓名、别名、绑定状态和微信名。内部目标解析需保留 `entity_id` 与对应 `wxid`，供程序查原话；群聊正文继续使用成员称呼，不输出内部标识。遇到同名、指代不清和未绑定成员时沿用现有消歧路径，不把相似称呼直接合并为一个人。
- **复用现有定向查询。** `recent_rows(room, sender_id=目标账号, since=窗口起点, before_id=当前消息锚点)` 已支持所需过滤；存储查询自身带当前 `account` 和 `room` 约束。程序使用已确认身份形成 `account+room+sender_id` 范围，再按本轮话题筛选相关发言，保留原始说话者、时间、消息 ID 和正文；只对必要的邻近上下文补读。人物档案和长期记忆用于背景，不据其中的人物标签猜测近期行为。来源：[recent_rows 实现](../wxbot_framework/conversation/history.py)。
- **分开本人原话与第三人描述。** “阿岚说过什么”优先使用阿岚自己的发言；他人谈到阿岚的记录标明原作者，作为第三人描述。两类材料均可与当前话题有关，但归因和支持强度分别呈现；机器人旧回复另保留来源标签，不充当本人陈述。阿岚为虚构示例名，不对应真实成员。
- **按任务组织答案。** 问具体说法就回答该说法及相关语境；问偏好就归纳相关选择；人物评价则先给有辨识度的概括，再以两三处具体发言、请求或互动支撑，说明行为与结论之间的关系。结论限定在实际观察范围；素材稀少时直接说明缺口，不补凑人格、动机或情节。
- **比较题使用相同窗口。** 比较两个人时采用相同起止时间和当前消息截止点，分别取得本人素材，再按相同维度归纳；说明材料覆盖差异，不因某人发言更多就默认某种特征更强。
- **表达和审核使用同一份材料。** 需要分析的回答容纳结论和例证，不硬套闲聊的极短字数；接梗可作简短补充。审核读取同一批原话及其归属，检查例证是否存在、归纳是否得到支持。已有材料充分时仍输出泛泛套话，应在回答生成与任务完成度上修正，避免只增加检索量。

验收分两部分。检索侧使用虚构成员及合成聊天，覆盖不含“评价”的人物提问、代词承接、当前话题相关性、目标原话被挤出全群 25 条、同名消歧、账号与群隔离、比较双方同一时间范围，以及本人原话与第三人描述的归属。生成侧固定一份已取得的材料，覆盖具体问题得到具体回答、多次同类请求能归纳出有依据的倾向、评价能用两三处例证支撑，并回放已有六条原话仍空泛的两条样本。两部分分别通过，避免把“已检索到材料”当作最终回答质量的验收终点。

## 7. 与现有规范的衔接及资料缺口

### 后续行为变更需要同步的规范

| 现有约定 | 本轮建议涉及的变化 |
|---|---|
| 艾特回复规范中模型失败仅记日志、本轮不发固定错误消息 | 若采用确定性的超时终态通知，需要更新失败行为及对应测试 |
| 搜索补查另有独立工具预算，修订链路可重复调用 | 改为一轮共享截止时间和有限调用次数后，需要同步预算说明 |
| 普通核对里“公开断言缺依据且本问确需查证”才搜索 | 将问题查证必要性单独用于搜索决策，修订判断另行使用 |
| 消息规范把换话题列为档案确认失效原因 | 改为按确认归属保留、明确取消/替换/过期失效，需要精确定义换题语义 |
| 图片索引只含启动后的接收图片、服务启动清空 | 自产媒体回填及跨重启范围需要补入消息、发送、生图规范 |
| 手册描述全群最近 50 条，代码默认 `group_limit=25` | 先按实际 25 条理解当前行为；人物相关上下文增加目标定向素材后，同步修正文档说明 |

来源：[艾特回复规范](../.spec/mention-reply/spec.md)、[消息规范](../.spec/messages/spec.md)、[发送规范](../.spec/delivery/spec.md)、[架构规范](../.spec/architecture/spec.md)。本表描述建议与现行约定的差异；没有据此修改规范或代码。

### 尚待本地定向验证

| 缺口 | 对设计的影响 | 最少需要的证据 |
|---|---|---|
| 当前原生图片发送的可用关联编号及自发回显 | 决定如何把自产图片绑定到引用 `svrid` | 同一张测试图的发送结果、回显、被引用事件字段，排除敏感 XML 密钥 |
| 发送原图与微信引用图片 MD5 的关系 | 决定 MD5 能否作为可靠关联路径 | 当前受支持微信版本的实际字段对照；含微信处理图片的情况 |
| “引用自产图编辑”的真实工具输入 | 决定是原图编辑还是重新按文字生成 | 可追踪的媒体解析结果和参考图参数；最终图回填后再次引用 |
| 各阶段真实延迟及取消能力 | 决定软提醒、普通回复截止、生图截止数值 | 分阶段耗时与底层 HTTP/线程取消结果；不得只看最终总耗时 |
| 设置优先级与持久范围 | 决定“只文字”覆盖群固定语音、随机语音和临时要求的顺序 | 当前所有发送选择入口及账号、群、成员设置的测试样例 |
| 生图服务是否提供任务查询/取消/幂等机制 | 决定超时后复用、等待或重新生成的动作 | 当前 Magpie 工具实际 schema 和调用返回字段 |

验收应至少包含：需要查证但初稿只说不知道；无依据具体病因/机制被去掉；明确问题得到答案而非只有接梗；设置后重启仍只发文字；别人插话后原成员仍能确认；后台任务被追问时状态准确；自产图引用看图与编辑均成功；预算耗尽有终态；取消和超时后迟到结果不发群；重复催促不重复生图；问答保持完整句和原有发送顺序。

## 来源与方法

实际浏览并核对了以上 GitHub 文件；主表使用固定 commit，官方协议及 Python 文档使用具体版本页面。Rasa、NoneBot 和 Haystack 先经 Context7 定位官方文档，再回到各项目源码核对。检索词只包含公开项目和机制名称，没有把真实群聊、成员身份或内部日志提交到外部搜索。

TypeSafe 部分核对了官方 cookbook 的原文。本文没有运行外部框架示例，也没有把示例中的阈值、成功率或耗时当作当前机器人效果。

本文采用外部项目中可独立移植的状态、关联和预算模式。具体 Jev 字段、时间阈值、SQLite 表结构、原生桥接字段及实现文件改动应由后续设计结合当前代码确定。
