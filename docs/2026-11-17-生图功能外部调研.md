# 生图功能外部调研

日期：2026-11-17。范围：为 helper 通过本机 Magpie MCP 生图提供外部设计依据；保持现有供应商选择。本报告只读取官方协议与项目维护者源码，未运行这些开源机器人，未执行付费生图。

证据标签：**文档**表示协议或维护者说明；**源码**表示已读取的实现；**推论**表示对 helper 的建议。Magpie 本机版本、工具 schema 与真实返回格式由主代理另行核对。

## 推荐结论

**推论：采用“接收请求并简短反馈 → 后台生成/查询结果 → 取得图片文件 → 复用微信图片发送”的窄流程。** 后台任务保留原会话目标；图片发送由程序负责，成功状态以发送链路返回结果为准。相关先例分别覆盖后台主动推送、微信图片发送和命令/工具入口差异。[后台推送源码](https://github.com/SanHans/astrbot_plugin_openai_image/blob/main/main.py#L1414-L1557)、[微信发送源码](https://github.com/iuiaoin/wechat-gptbot/blob/8960ef806262eef4e43acee27b440a503897c07a/channel/wechat.py#L196-L209)

**推论：若本机工具已经提供生成 ID 与结果查询，就沿用它完成等待。** 首次发起和后续查询应分开记录，网络超时后保留已取得的 ID；自动再次发起生成应有服务端幂等依据。MCP 2025-03-26 的连接中断与取消分别有独立语义，取消通知也可能因操作无法取消而被忽略。[HTTP 中断语义](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports#sending-messages-to-the-server)、[取消规则](https://modelcontextprotocol.io/specification/2025-03-26/basic/utilities/cancellation#behavior-requirements)

## 三个开源先例

### 1. AstrBot OpenAI Image：后台生成后主动发图

**源码：** `draw_image` 将任务交给 `_queue_generation_task`；后者创建后台协程并携带 `unified_msg_origin`。`_run_generation_task` 在信号量内请求生成，再走 `_send_success_response`，最终用 `context.send_message` 投递到原会话。图片收集支持 Base64 落盘及 URL 下载，两种来源汇入本地图片消息链。[命令与排队](https://github.com/SanHans/astrbot_plugin_openai_image/blob/main/main.py#L1522-L1626)、[生成与投递](https://github.com/SanHans/astrbot_plugin_openai_image/blob/main/main.py#L1318-L1464)

**可借鉴（推论）：** 接收入口尽早释放；将目标会话与任务绑定；生成与图片投递各自有明确结果。helper 只需接入 Magpie 调用与现有图片发送接口。

**局限（源码）：** 后台任务集合保存在内存，插件终止时会取消任务；这套实现没有在此链路提供重启后的任务恢复。该项目还带有多图编辑确认、润色及供应商参数，本文只采用其任务与投递结构。[初始化与终止](https://github.com/SanHans/astrbot_plugin_openai_image/blob/main/main.py#L210-L258)

### 2. wechat-gptbot：明确图片回复类型，再交给微信通道

**源码：** 群聊先判断艾特，再通过图片前缀设置 `ContextType.CREATE_IMAGE`。生成函数返回 `Reply(ReplyType.IMAGE, image_url)`；微信通道对图片执行 `serialize_img`，随后把路径与群/私聊目标交给 `send_image`。[入口路由](https://github.com/iuiaoin/wechat-gptbot/blob/8960ef806262eef4e43acee27b440a503897c07a/channel/wechat.py#L101-L135)、[生成结果](https://github.com/iuiaoin/wechat-gptbot/blob/8960ef806262eef4e43acee27b440a503897c07a/bot/chatgpt.py#L24-L54)、[微信图片发送](https://github.com/iuiaoin/wechat-gptbot/blob/8960ef806262eef4e43acee27b440a503897c07a/channel/wechat.py#L196-L209)

**可借鉴（推论）：** 图片应作为独立交付类型进入发送层；群聊接收目标沿用原消息元数据。首版使用明确的生图入口，容易控制触发与验收。

**局限（源码）：** 该快照在消息处理内同步调用生成，`reply_img` 使用该项目自己的供应商 SDK。参考其消息分层即可，后台等待方案采用前一个先例。[同步调用点](https://github.com/iuiaoin/wechat-gptbot/blob/8960ef806262eef4e43acee27b440a503897c07a/channel/wechat.py#L155-L194)

### 3. AstrBot AI Media：命令发图片，LLM 工具返回文本

**源码：** `/picture` 入口先给出处理提示，随后 `await _generate_image` 并 `yield event.image_result(url)`；其注册给 LLM 的 `_draw` 则返回包含 URL 的普通字符串。[命令入口](https://github.com/lcrworld-jtl/astrbot_ai_media/blob/main/main.py#L523-L546)、[工具入口](https://github.com/lcrworld-jtl/astrbot_ai_media/blob/main/main.py#L399-L437)

**可借鉴（推论）：** 生成函数可以共用，但每个入口都要明确谁负责发图。若 helper 将来加入自然语言调用，工具结果应交给同一图片交付流程；用户实际收到图片应成为验收条件。

## MCP 官方协议对接要点

以下以 **2025-03-26** 为接入参考，客户端应按实际协商版本使用能力。该版初始化交换版本与能力，随后发送 `notifications/initialized`。[生命周期规范](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle#initialization)

| 主题 | 文档事实 | 对 helper 的设计含义（推论） |
| --- | --- | --- |
| 图片结果 | `content` 可含多个项目；标准图片项目是 `type: image`、Base64 `data` 与 `mimeType`。[Tools](https://modelcontextprotocol.io/specification/2025-03-26/server/tools#tool-result) | 按返回类型提取图片字节；文本里的 URL 按 Magpie 实际格式单独处理。 |
| 工具错误 | JSON-RPC `error` 与工具结果 `isError: true` 是两个错误通道。[错误处理](https://modelcontextprotocol.io/specification/2025-03-26/server/tools#error-handling) | HTTP 请求成功之后继续检查这两层，再判断图片是否可交付。 |
| 进度 | 调用方可传 `_meta.progressToken`；服务端可以完全不发进度，也可省略总量。[Progress](https://modelcontextprotocol.io/specification/2025-03-26/basic/utilities/progress) | 按结果查询状态展示“处理中”；没有依据时不展示百分比。 |
| 时限 | 应设置每请求超时；收到进度可延长计时，但仍应有最大时限。超时后应请求取消并停止等待。[Timeouts](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle#timeouts) | 单次 MCP 调用时限与整项生图等待时限分开；具体数值按 Magpie 等待窗口和实测耗时确定。 |
| HTTP 返回 | 客户端须支持 JSON 与 SSE 两种响应；SSE 中最终响应前可以有通知。[HTTP](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports#sending-messages-to-the-server) | 复用支持该格式的现有 MCP 客户端，并按请求 ID 取最终结果。 |
| 中断与取消 | 本版连接断开后服务端可能继续执行；接收方允许忽略无法取消的请求。[HTTP](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports#sending-messages-to-the-server)、[Cancellation](https://modelcontextprotocol.io/specification/2025-03-26/basic/utilities/cancellation#behavior-requirements) | 区分“停止等待”“请求取消”“确认取消”；缺少确认时保留任务 ID 与结果未知状态。 |

**版本边界（文档）：** `2025-06-18` 的工具结果文档列出 `resource_link`、`structuredContent` 与 `outputSchema`；`2026-07-28` 又采用每请求版本元数据及扩展协商，Tasks 由扩展承载。它们分别属于对应版本的约定。[2025-06-18 Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#tool-result)、[2026-07-28 Versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)、[Tasks 扩展](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks)

**建议（推论）：** 本次只实现已核对的本机工具行为，保持当前协议版本与结果格式；后续服务器升级时再评估新格式或 Tasks。

## 形成最终设计前需要补齐的本机证据

下列是待验证项，不作已完成功能描述：

- 一次成功返回、一次处理中返回、一次失败返回的准确字段；图片与 URL 是否同时出现。
- 生成 ID 的有效期、结果查询是否可重复、机器人重启后是否仍可查询。
- 取得 ID 前断连的行为，以及结果查询超时后可用的继续查询方式。
- 本地图片经现有微信发送接口的真实结果、发送后文件可清理的时机。

**建议验收（推论）：** 至少覆盖立即成功、凭 ID 等待后成功、工具失败、等待超时、生成成功但微信发送失败。重试投递时复用已生成图片；重新生成作为新的明确请求处理。
